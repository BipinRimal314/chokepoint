Notes from a cluster · chokepoint

Where do you stand?

You want to put a guard in front of a program. The program has no front door. This is the whole problem, and everything else follows from it.

17–18 August 2026 · single-node k3s v1.36.3 · Arch Linux

Here is a puzzle. An AI agent is doing work on your machine — reading files, writing files, running searches. It does this by talking to a tool server: a separate program that owns the actual filesystem access. You would like to watch that conversation. Better, you would like to be able to stop it: if the agent asks to read ~/.ssh/id_rsa, you want something to say no.

So: where do you stand?

The instinct — and it is a good instinct, because it is right nearly everywhere else — is to stand in the network. That is what we always do. Traffic flows from A to B, you put a proxy in the middle, and now you see everything and can refuse anything. Every firewall, every service mesh, every API gateway is this idea. It works because there is a place to stand: a port, a socket, a hop.

Now the awkward part. The Model Context Protocol, which is how these agents talk to their tool servers, most commonly runs over something called stdio. Standard input and standard output. Pipes.

What that means concretely: the agent does not connect to the server. The agent launches the server, as a child process, and they talk through the pipes that connect a parent to its child. There is no port. There is no socket. There is no packet that ever leaves the process pair.

There is no network hop, so there is nowhere in the network to stand. A proxy deployed beside this thing would have nothing on its stdin. It would proxy nothing, forever, quite successfully.

This is worth sitting with, because it is the kind of constraint that quietly invalidates a lot of received wisdom. You cannot sidecar your way out of it. You cannot point a Service at it. The usual shape of security infrastructure assumes a chokepoint exists in the network, and here one simply does not.

So find a different constriction

But notice what we do have. The agent has to launch the server. That launch — the exec — is a real event, and it is a narrow one. Everything the agent is about to do goes through a program it is about to start.

So: be that program.

You tell the agent to launch chokepoint instead of the real server, and you hand chokepoint the real server's command line. chokepoint starts the real server as its own child, and sits in the middle relaying bytes. Requests come down from the agent, chokepoint reads them, and either passes them along or refuses them and sends back a denial. The agent thinks it is talking to the filesystem server. The filesystem server thinks it is talking to the agent. Neither is wrong about anything that matters to them.

The network had no chokepoint, so we made one out of the process tree. That is where the name comes from.

Which wrecks the deployment, in an interesting way

Follow the consequence. If chokepoint has to be the process the agent spawns, then chokepoint has to be inside the agent's container at the moment of spawning. Not in a pod next door. Not behind a Service. In the same filesystem namespace, on disk, ready to be executed.

Which means you do not deploy this thing. You deliver it.

That inverts how security tooling normally arrives. Usually the tool is a service and the workload talks to it. Here the tool is an artifact, and it has to be placed where other pods can pick it up. There is exactly one well-known Kubernetes pattern shaped like that, and it is the one CNI network plugins use: a DaemonSet whose job is to copy a file onto every node and then get out of the way.

So the DaemonSet does not run chokepoint. Read that again, because it is the part that confuses everyone: chokepoint-installer never proxies anything. An init container downloads the release, checks it, writes the binary to /opt/chokepoint/bin on the host, and exits. The pod that remains holds a pause container — a program whose entire purpose is to do nothing, cheaply, so that the pod stays alive and Kubernetes will re-run the install whenever the node reboots or the version changes.

One detail in that diagram is doing more work than it looks. The install writes to a temporary name and then mv -fs it into place. Renaming within a single filesystem is atomic — the kernel guarantees it — so an agent that happens to exec during an upgrade gets either the whole old binary or the whole new one. Never half a file. Copy directly over the target instead and you have invented a rare, unreproducible crash.

The part where you find out

All of the above was designed, written, documented, and tested — and had never once run on a real cluster. That is an uncomfortable amount of confidence to hold on the strength of unit tests, so: k3s on a single node, four commands, and see.

Two applies, a wait, and a look at the log:

$ kubectl apply -f 10-installer-daemonset.yaml
namespace/chokepoint-system created
daemonset.apps/chokepoint-installer created

$ kubectl apply -f 20-policy-configmap.yaml
namespace/agents created
configmap/chokepoint-policy created
configmap/agent-mcp-config created

$ kubectl -n chokepoint-system rollout status ds/chokepoint-installer
daemon set "chokepoint-installer" successfully rolled out

And then the moment of truth, which is two lines long:

$ kubectl -n chokepoint-system logs ds/chokepoint-installer -c install
chokepoint_0.1.0_linux_amd64.tar.gz: OK
chokepoint 0.1.0

The second line is the one you go looking for. The first line is the one that matters more: that is sha256sum -c passing. The checksum was fetched, the archive was checked against it, and only then was anything unpacked. Unattended, inside the cluster, with nobody watching.

Was anything actually staged, though? A log line is a claim, not evidence. On the host:

$ ls -la /opt/chokepoint/bin/
-rwxr-xr-x root root 20M chokepoint

$ /opt/chokepoint/bin/chokepoint --version
chokepoint 0.1.0

$ sha256sum /opt/chokepoint/bin/chokepoint
8b663bbb9d592a07882b259b301d7485ddaaceca3a425b529fe4590a3ac145b7

Then, separately, pull the published archive by hand, verify it, unpack it, and compare. Byte-identical. The thing on the node is the thing that was released — not something like it.

Everything passed on the first attempt. Which is pleasant, and also slightly suspicious, because a test that has only ever succeeded has not told you very much.

So break it deliberately

The README makes a promise about failure. Point the installer at a version that does not exist, it says, and the install "fails loudly on a 404 rather than staging nothing quietly."

That is a good promise, and the quiet failure is exactly the one you would fear. Imagine it going the other way: you bump a version, the download 404s, the script shrugs, the pod reports success, and every agent on that node carries on execing a binary that is silently months out of date — or absent, so the agent falls back to running the tool server directly, with no guard at all. You would never look. The dashboard would be green.

So we set the version to 9.9.9, which has never existed, and applied it.

$ kubectl -n chokepoint-system rollout status ds/... --timeout=60s
error: timed out waiting for the condition   (rc=1)

$ kubectl -n chokepoint-system get pods
NAME                         READY   STATUS         RESTARTS
chokepoint-installer-cj8w8   0/1     Init:Error     3

$ kubectl ... logs ds/chokepoint-installer -c install
wget: server returned error: HTTP/1.1 404 Not Found

Loud at three separate levels, which is what you want, because different people look in different places. The rollout command exits non-zero, so CI catches it. The pod status says Init:Error with a climbing restart count, so a dashboard catches it. And the log says, in plain words, exactly what went wrong — so a human catches it.

That last one was not guaranteed. The script calls wget -q, and quiet mode in some implementations suppresses the error along with the progress bar. Had that been true here, the pod would have failed with a completely empty log — loud in status, mute in the one place the documentation tells you to look. It prints. But that is a property of this wget, not something the script enforces, and it is the kind of thing that changes underneath you when a base image is bumped.

Now the more important half. While the installer was failing and restarting, what happened to the binary already on the node?

PropertyBeforeDuring failure
versionchokepoint 0.1.0chokepoint 0.1.0
sha2568b663bbb…8b663bbb…
mtime17:46:5317:46:53
.chokepoint.tmpabsentabsent

Untouched. Same bytes, same timestamp, still runs. The download fails before anything reaches the staging directory, so a botched upgrade cannot damage a working install — and it leaves no temporary file behind to confuse the next attempt. Agents on that node keep running the guard they already had. Setting the version back and re-applying brought the pod up clean and printed chokepoint 0.1.0 again, which incidentally proves the reconcile claim too: changing that one environment variable really does re-run the install, in both directions.

None of which is the point

Everything so far is about a file arriving on a machine. Verified, atomic, reconciling, failing loudly — all true, and all of it describes a package manager. It says nothing whatsoever about whether the program does its job once it is there. It is entirely possible to build a flawless delivery pipeline for a guard that, on arrival, guards nothing.

So the next day, the actual question: does an agent pod exec that staged binary instead of its tool server, and does a rule fire?

Setting this up has a trap in it that is worth pointing out, because it is the trap most likely to catch a real deployment. The obvious way to write this test is to have the test spawn chokepoint and talk to it. That test always passes. It also proves nothing, because the thing most likely to go wrong in a real cluster is not chokepoint failing — it is chokepoint never being invoked. You mount the binary, you mount the policy, you feel protected, and the agent's config still names the tool server directly. Every mount is correct. The proxy is not in the path.

So the stand-in agent here reads the same mcp.json a real client would read, and launches whatever that file names. If the wiring is wrong, it talks straight to the server, everything is permitted, and the test fails loudly instead of passing for the wrong reason.

Who is whose child

The claim under the entire design is that interception happens by process ancestry. That is checkable directly. From inside the running pod, reading /proc:

pid=1   ppid=0  python3 -u /opt/testkit/driver.py
pid=7   ppid=1  /opt/chokepoint/bin/chokepoint --policy /etc/chokepoint/policy.yaml …
pid=18  ppid=7  python3 /opt/testkit/mock_mcp_server.py

Read the middle column. The agent's child is chokepoint. chokepoint's child is the tool server. There is no arrangement of those three processes in which the agent reaches the server without passing through pid 7 — not because a rule forbids it, but because the pipe goes where it goes. And the binary at pid 7 is the one the DaemonSet staged the day before, from the hostPath, unchanged.

That is the doorway, and something is standing in it.

Seven calls

Now make it refuse things. The session is seven tool calls, each one aimed at a specific rule in the policy:

The agent asks to…VerdictBecause
read a file in its workspaceallow— the control
read an SSH private keydenyno-credential-paths
read the pod's Kubernetes tokendenyno-serviceaccount-token
read /etc/passwddenyoutside-declared-workspace
reach cloud metadata at 169.254.169.254denyno-cloud-metadata
read that same workspace file againdenytool-definition-changed
write a file in its workspaceallowaudited by watch-writes

Seven for seven, in-cluster, against the staged binary. But do not skim past the first row. A test in which everything is denied is not a test — a proxy that has crashed into a closed pipe denies everything too, and produces a table that looks exactly like success. The allowed call is what distinguishes enforcement from breakage.

Now look at rows one and six. They are the same call. Byte for byte, the same tool, the same path, the same arguments. Allowed the first time, refused the second.

Nothing about the agent changed between them. What changed is that the server quietly rewrote its own description of the tool — same name, same schema, same everything a program would validate — while altering the natural-language instructions that a language model actually reads and obeys. This is a real attack shape, and a nasty one, because every individual call remains perfectly well-formed. There is nothing wrong with the request. The wrongness is in what the tool now claims to be.

level=WARN msg="tool definition changed since first listing" tool=read_file
  kind=modified listing=2
  was=f435ed4344fe7fb5…  now=dfa786ba87ee16a4…

The proxy holds the server to what it published the first time it was asked. It cannot know whether the first description was honest — it can only know that this one is different, and that nobody approved the change.

Meanwhile the metrics endpoint served forty-five series to a scrape from a completely separate pod, and the audit log held seven lines for seven calls — allows recorded alongside denials, which is the half people forget. A log that only records refusals cannot tell you what an agent actually did on the day you need to know.

Break that too

Same discipline as before: the documentation makes a promise about failure, so go and collect on it. The promise this time is that a policy which does not compile stops the agent rather than quietly waving it through.

This is the failure that should frighten you most. A typo in a rule is not an exotic event; it is a Tuesday. And the tempting, friendly behaviour — log a warning, skip the broken rule, keep serving — produces an agent running with protection its operator is certain is in place. So: break one rule's syntax, mount it, apply.

$ kubectl -n agents rollout status deploy/... --timeout=60s
error: timed out waiting for the condition   (rc=1)

$ kubectl -n agents get pods
interception-broken-policy-…   0/1   CrashLoopBackOff   3

$ kubectl -n agents logs deploy/... -c agent
chokepoint: load policy: rule "watch-writes": ERROR: <input>:1:18: Syntax error:
 | tool.startsWith( || tool.startsWith("delete")
 | .................^

It names the rule and points at the column, which is the difference between a five-minute fix and an hour of bisecting a YAML file. But the more interesting part is what happens to the agent. The proxy exits. The pipe closes. The agent process dies with it.

A broken configuration produces an agent with no tools at all — not an agent with unguarded ones. The failure is closed.

Which is the right way round, and I want to be precise about why it happens, because it would be easy to award chokepoint credit it has not earned. That behaviour is a property of the arrangement, not of the program. It fails closed because the agent's only route to a tool server runs through a process that refused to start. An MCP client that responded to a failed launch by falling back to spawning the server directly would convert this exact same event into a silent bypass — green agent, working tools, no guard. Nothing in this design prevents that. It is a property of the client you happen to be running.

The first principle

Feynman's line about science is that the first principle is that you must not fool yourself — and you are the easiest person to fool. It applies with unusual force to security tools, because a security tool that does not work looks exactly like a security tool that does, right up until it matters.

So here is the honest accounting for this one. chokepoint scores a session for how much it looks like a decomposed sweep — an agent quietly touching a very large number of things. The scoring has published, measured, unflattering limits:

  • It is blind to scale. One tool used against any number of distinct targets scores exactly 0.400. Twenty targets, twenty thousand targets — same number. A threshold cannot separate what does not differ.
  • Novelty falls off a cliff, not a slope. Over a looping vocabulary of twenty tools, the novelty signal reads 1.000 at twenty calls, 0.050 at forty, and 0.000 from sixty onward. A quarter of the scoring weight is inert for any session of real length.
  • Being erratic makes you look worse, not better. Randomising which tool comes next raises the score — 0.757 against 0.618 for the same vocabulary walked in a boring cycle. The evasive strategy and the sophisticated-looking strategy point in opposite directions.
  • A bigger theft is not a louder one. Breadth saturates against session length, so the cost of hiding does not grow with the size of what you are taking.

And the deployment has its own limits, which today's exercise did nothing to remove:

  • The binary is trusted because of its checksum, and the checksum is served by the same host as the binary. That catches corruption. It does not catch a compromised release.
  • A hostPath is a hostPath. Any pod that can mount /opt/chokepoint/bin writable can replace the binary every agent on that node then execs.
  • Nothing here stops an agent from going around the proxy. An agent that can exec arbitrary commands can exec the tool server directly. This is a control on a configured path, not a sandbox.

And the cluster run said so itself, in a way I did not plan and rather like. Every metric came back populated — calls, denials, audits, targets — except one:

chokepoint_policy_denials_total{rule="tool-definition-changed"}  1
chokepoint_tool_calls_total{effect="deny"}                       5
chokepoint_session_targets                                     6
chokepoint_decomposition_score                               NaN

Not zero. NaN — the detector declining to answer, because seven calls is not a session and it will not pretend otherwise. That is the correct behaviour, and reporting 0.0 instead would have been a small lie of exactly the kind that gets believed: a dashboard reading zero looks like an agent behaving well, not like a question nobody asked.

But sit with what the run therefore demonstrated. Every rule that fired was a deterministic one — this path, that prefix, this definition changed. The behavioural detector, which is the part with the research in it, never spoke at all. The enforcement machinery works. The judgement it is supposed to enforce did not get tested, because it had nothing to judge.

Inline enforcement buys you enforcement. It does not buy you detection. Standing in the doorway means you can refuse — it does not mean you can tell who you should be refusing.

That distinction is the actual result, and it is easy to lose. Being able to say no, at the exact moment a tool call is made, with the authority to make the refusal stick, is genuinely worth having; it is a different and better thing than reading a transcript afterwards and filing a report. But moving the detector into the request path does not make the detector smarter. The blind spots travel with it.

So, precisely, what these two days established. The delivery mechanism works: the binary arrives, it is verified before it is unpacked, it lands atomically, a bad version fails loudly without damaging a good install, and the whole thing reconciles. And the guard works where it lands: it really is in the process path, it really does refuse, and it refuses a call it had allowed ten milliseconds earlier once the server changed its story.

What they did not establish, stated with the same precision, because this is the half that gets quietly dropped:

  • The agent was a stand-in, and so was the server. Fifty lines of Python speaking JSON-RPC is not Claude Code, and a mock server is not npx pulling a real filesystem server with its own runtime requirements. The claim that a real client's config has the shape this deployment expects is still a claim.
  • Only the deterministic rules ran. Path matching, scope containment, definition fingerprinting — yes. Anything that depends on the shape of a session over time — no. See the NaN.
  • One node. Everything about how this behaves across a real cluster remains inference.

None of which is a disappointing result. It is just a smaller one than "we tested it and it works", and the gap between those two sentences is where most security claims quietly go wrong. The next thing to find out is what happens when a real agent, running a real tool server, does something long and strange enough that the detector has to give an actual number — and whether that number is any good.
